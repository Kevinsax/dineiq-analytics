# AI Tool Usage Declaration

in this project, what it produced, and — critically — what the team itself
did to review, run, test, and understand that output before it became part
of this submission. Per the SRS: *"Teams must not directly submit content or
code generated by GPTs or other AI tools without independently reviewing,
modifying, testing, and understanding it."*

## 1. Debugging Pair A's Spark pipeline

- **Purpose of use:** fix real runtime errors hit while executing the
  delivered ingestion/cleaning scripts against the team's actual generated
  dataset on Windows.
- **Type of assistance requested:** error diagnosis and a corrected code
  patch for each reported traceback.
- **Files/modules affected:** `spark_jobs/data_quality_report.py`,
  `spark_jobs/clean_data.py`.
- **Modifications performed:** replaced `to_date()` with `try_to_date()` in
  the date-validity checks so a single malformed date (`"2025-13-45"`) is
  counted as invalid rather than crashing the job with
  `DateTimeException: [CANNOT_PARSE_TIMESTAMP]`; then fixed a second bug
  where `try_to_date()`'s format argument was passed as a `lit(...)` column
  (causing `PySparkTypeError: [NOT_ITERABLE]`) instead of a plain string.
- **Testing completed:** the team re-ran both scripts against the full-scale
  dataset on their own machine after each fix and confirmed the scripts
  completed without error and produced the expected data-quality counts.
- **Verified by:** [Adeshina Adekunle]

## 2. Debugging Pair B's classification handoff

- **Purpose of use:** resolve a file-format mismatch reported by the team
  after running the delivered classification scripts (Spark output was a
  Parquet *folder* of part-files; the Python-side output was a single file,
  and the CSV export the team expected was missing entirely).
- **Type of assistance requested:** code fix so both pipelines' outputs are
  consistent, single-file, and include a CSV export.
- **Files/modules affected:** `spark_sql/classify_spark.py`,
  `python_pipeline/classify_python.py`.
- **Modifications performed:** added a `.to_csv(...)` export to both
  scripts; changed `classify_spark.py` to convert its result to pandas
  (`.toPandas()`) before writing Parquet, so its output is a single file
  matching `classify_python.py`'s output shape instead of a Spark-native
  partitioned folder.
- **Testing completed:** the team re-ran both scripts on their own machine,
  confirmed both `data/models/item_classification_spark.parquet` and
  `item_classification_python.parquet` were now single files openable the
  same way, and confirmed the CSV exports opened correctly in Excel.
- **Verified by:** Caleb Edoho

## 4. Building the Pair C application (new code)

- **Purpose of use:** build the dashboard/application layer (Pair C) —
  demand forecasting, the recommendation engine, and the eight-page
  Streamlit application — reading directly from Pair B's real handoff
  files.
- **Type of assistance requested:** full implementation of new scripts and
  application pages, plus a matching step-by-step build/run guide.
- **Files/modules affected:** `src/utils.py`, `src/Executive_Dashboard.py`,
  `src/pages/1_Menu_Intelligence.py` through `7_What_If_Simulator.py`,
  `python_pipeline/build_forecast.py`, `python_pipeline/build_recommendations.py`,
  `documentation/DineIQ_5_PairC_StepByStep_Guide.docx`.
- **Modifications performed:** this code was generated new rather than
  modifying existing team code; it was then hardened after review — a bug
  was found and fixed where `Executive_Dashboard.py`'s critical-recommendation
  section wrapped a Streamlit data loader in `try/except Exception`, which
  cannot catch Streamlit's `st.stop()` (a deliberate `BaseException`
  subclass), so the intended graceful-degradation path could never run; this
  was fixed by checking `os.path.exists(...)` directly instead. Several
  unused imports, a malformed emoji escape sequence, and a broken ternary
  expression found during manual code review were also cleaned up.
- **Testing completed:** the AI's own logic (for `build_forecast.py` and
  `build_recommendations.py` specifically) was validated by running pandas-only
  simulations against the team's actual full-scale generated CSV data before
  handoff, so the forecasting and recommendation numbers reflect the real
  dataset rather than invented figures. The team then independently installed
  and ran the full application on their own machine against their own
  full-scale pipeline output, and confirmed it live end-to-end — including a
  screenshot of the running Executive Dashboard showing real computed totals
  (Total Revenue, Total Profit, Total Orders, active customers, menu item
  count) that matched what the pipeline output predicted.
- **Verified by:** Oyibo Nuhu & Anieto

## Statement on final analytical outputs

Per the SRS's own requirement: *"The final restaurant analytics,
predictions, classifications, recommendations, and forecasts must be
produced by the team's own Spark, Python, Data Science, Machine Learning,
and application logic."* All classification labels, RFM segments, basket
rules, wastage rankings, and demand forecasts shown in the application are
computed by the team's own pipeline scripts (several of them authored with
AI assistance as declared above, then run and verified by the team) executing
against the team's own generated dataset — no analytical result in this
project is hard-coded, mocked, or produced directly by an AI tool without
running through that pipeline.
